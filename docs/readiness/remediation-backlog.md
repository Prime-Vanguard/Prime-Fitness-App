## Required behavioral scenarios

1. Approve the same pending PV claim from two connections: one terminal decision, one ledger award, one consistent audit outcome. Repeating with the same idempotency key returns the original result; rejection and resubmission cannot bypass eligibility.
2. Redeem the final inventory unit concurrently with insufficient-balance and cancelled/refund cases: never negative balance/stock; refund original price only once; price changes cannot alter earlier receipt.
3. Change coach/leader role or pause staff while a token and editor are open: next sensitive request denies/revalidates, local draft remains recoverable.
4. Import the same source workout after mapping/file order changes or lost chunk response: one accepted history item, no XP/streak/schedule effect; edited import and restore retain provenance.
5. Save decimal/cleared/imperial weights, paired unilateral/drop/timed sets and missing RPE: correct canonical values, counts/PR eligibility, no background timer dependency.
6. Save food/favorite/water/wellness/measurements across restart, quota error, simultaneous tabs, deletion in flight and expired login: preserve local intent and distinguish server acceptance.
7. Exercise Cairo midnight/DST, travel and overnight page use; old plans retain frozen prescription and old logs retain nutritional/exercise snapshots.
8. Upload real synthetic image binaries: malicious MIME, oversize/EXIF, unauthorized signing/download/delete, cancelled upload and delayed cleanup.
9. Service worker must not cache private API responses, photos or mutation requests; migration/update must not clear pending IndexedDB work.
10. Deleted member/withdrawn consent must follow approved retention and restore-suppression policy, including exports, telemetry and backups.

## Roadmap and effort control

Maintain one reviewed change at a time for P1 security/data work. Each patch includes source tests, isolated integration evidence and a recovery note before release. Never combine migration reconciliation with a large UI refactor.

The founder should budget 10 focused oversight/acceptance hours per week and 2–3 support hours during beta. These are planning assumptions, not measured available capacity. Weekly planning selects only work that fits; uncompleted launch gates move the launch date. The 90-day sequence in the blueprint is conditional, not a delivery guarantee.

Beta cohort: founders/staff first, then 10 invited adult members in the approved jurisdiction; expand to 20 after 14 days without integrity/privacy incidents, with functioning restore/alerts and support response capacity. Consider 50 only after another capacity review. These are proposed rollout limits, not measured infrastructure maximums.
